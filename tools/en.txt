>>> 07 · ЕЩЁ ФИШКИ

>>> Что ещё продумано
<<< What else is built in
>>> <h3>Субагенты</h3><p>Главный агент может запускать помощников. У каждого свой паспорт с пометкой <code>parent_agent</code>. Сами к Person Server они не ходят: пропуска для них берёт родитель. Глубина только один уровень.</p>
<<< <h3>Sub-agents</h3><p>A main agent can spawn helpers. Each gets its own passport marked with <code>parent_agent</code>. They never call the Person Server themselves: the parent gets their passes. Only one level deep.</p>
>>> <h3>Цепочки вызовов</h3><p>Сервис, которому для ответа нужен другой сервис, сам становится агентом со своим паспортом. Права человека передаются по цепочке, и Person Server видит каждое звено.</p>
<<< <h3>Call chaining</h3><p>A service that needs another service to answer becomes an agent itself, with its own passport. The person’s authority flows down the chain, and the Person Server sees every link.</p>
>>> <h3>Нет «вечных» токенов</h3><p>Паспорт агента живёт до 24 часов, токен личности до часа, заявка до 5 минут. Refresh-токенов нет: когда пропуск истёк, агент снова спрашивает сервис, и у сервиса есть право сказать «нет».</p>
<<< <h3>No forever tokens</h3><p>An agent passport lasts up to 24 hours, a person token up to an hour, an access request up to 5 minutes. There are no refresh tokens: when a pass expires, the agent asks the service again, and the service can say no.</p>
>>> <h3>Отзыв каскадом</h3><p>Отозвал токен личности, и Person Server сообщает об этом сервису и серверу доступа. Тот, в свою очередь, гасит все пропуска, выданные по этому токену.</p>
<<< <h3>Cascading revocation</h3><p>Revoke a person token and the Person Server tells the service and the access server. The access server in turn cancels every pass it issued against that token.</p>
>>> <h3>Приватность</h3><p>Для каждого сайта у тебя свой псевдоним (<code>sub</code>). Сайты не могут сопоставить тебя между собой. В режимах 3–5 сервис даже не видит, какой именно агент пришёл, поэтому не может пускать «только агентов от компании X».</p>
<<< <h3>Privacy</h3><p>You get a different pseudonym (<code>sub</code>) at every site, so sites can’t link you to each other. In modes 3–5 the service doesn’t even see which agent product showed up, so it can’t admit “only agents from company X.”</p>
>>> <h3>Честное окно согласия</h3><p>Person Server обязан визуально отделять слова агента («мне нужно, потому что…») от того, что заявил сам сервис. Агенту выгодно, чтобы ему поверили, и ты должен видеть, где чьи слова.</p>
<<< <h3>An honest consent screen</h3><p>The Person Server must visually separate the agent’s words (“I need this because…”) from what the service itself declared. The agent gains from being believed, so you should see who said what.</p>
>>> <h3>Внедрять можно по частям</h3><p>Каждая сторона подключается сама по себе. Сервис может начать с проверки подписи вместо API-ключа. Тот, кто AAuth не знает, просто игнорирует новые заголовки, и всё старое продолжает работать.</p>
<<< <h3>Adopt it piece by piece</h3><p>Each party joins on its own. A service can start by checking signatures instead of API keys. Anyone who doesn’t know AAuth simply ignores the new headers, and everything old keeps working.</p>
>>> <h3>Целое семейство черновиков</h3><p>Рядом с основным протоколом развиваются отдельные документы: Budgets (лимиты трат агента), Events (уведомления агентам), R3 (права в терминах MCP, OpenAPI, gRPC, GraphQL) и Bootstrap (как агент получает паспорт).</p>
<<< <h3>A whole family of drafts</h3><p>Separate documents grow alongside the core protocol: Budgets (agent spending limits), Events (notifications to agents), R3 (permissions in MCP, OpenAPI, gRPC and GraphQL terms) and Bootstrap (how an agent gets its passport).</p>

>>> 09 · ВОПРОСЫ
<<< 09 · FAQ
>>> Частые вопросы
<<< Frequently asked questions
>>> <summary>Это уже можно использовать?</summary><p>Попробовать можно: есть SDK для TypeScript, .NET, Python и Go, расширение для Keycloak, готовый Person Server и демо-песочницы (AAuth Explorer, AAuth Web Agent). Но это черновик, а не стандарт. Между версиями меняются названия полей и даже число режимов, так что для боевых систем пока рано.</p>
<<< <summary>Can I use it today?</summary><p>You can try it: there are SDKs for TypeScript, .NET, Python and Go, a Keycloak extension, a ready-made Person Server and demo playgrounds (AAuth Explorer, AAuth Web Agent). But it’s a draft, not a standard. Field names and even the number of modes change between versions, so it’s too early for production.</p>
>>> <summary>Это замена OAuth?</summary><p>Нет, скорее надстройка для мира агентов. Обычные приложения с OAuth продолжат работать как раньше. Сервис может спрятать свой OAuth-токен внутрь сессионного токена AAuth, а Person Server может логинить людей через OpenID Connect.</p>
<<< <summary>Does it replace OAuth?</summary><p>No, it’s more of a layer for the world of agents. Regular apps with OAuth keep working as before. A service can wrap its OAuth token inside an AAuth session token, and a Person Server can sign people in with OpenID Connect.</p>
>>> <summary>Что изменится для обычного человека?</summary><p>Появится место, где видно всех твоих агентов: какие подключены, на каких устройствах, какие у них задания и что они уже сделали. Там же можно ответить на вопрос агента, разрешить или запретить действие и отозвать доступ. Это и есть Person Server.</p>
<<< <summary>What changes for an ordinary person?</summary><p>You get one place that shows all your agents: which are connected, on which devices, what tasks they have and what they’ve already done. That’s also where you answer an agent’s question, allow or block an action, and revoke access. That place is your Person Server.</p>
>>> <summary>А если украдут сам секретный ключ агента?</summary><p>Тогда провайдер агента перестаёт выдавать ему паспорт и отзывает текущий через Person Server. Паспорт живёт не больше суток, токен личности не больше часа. Есть слабое место: сервис, который пускает агента только по паспорту (режим 1), сообщения об отзыве не получает. Там доступ закончится, когда истечёт паспорт.</p>
<<< <summary>What if the agent’s secret key itself is stolen?</summary><p>Then the agent provider stops issuing it passports and revokes the current one through the Person Server. A passport lasts at most a day, a person token at most an hour. There is one weak spot: a service that admits the agent on its passport alone (mode 1) never hears about the revocation, so there access ends only when the passport expires.</p>
>>> <summary>Как это связано с MCP?</summary><p>MCP сейчас использует OAuth 2.1 и динамическую регистрацию клиентов: на каждом сервере у агента новый client_id, а токены на предъявителя. Автор AAuth приводит MCP как пример, где эти ограничения уже мешают. Для MCP-серверов уже есть реализации AAuth: TypeScript SDK для MCP-серверов и модуль для Envoy и agentgateway, который превращает MCP-сервис в AAuth-ресурс.</p>
<<< <summary>How does this relate to MCP?</summary><p>MCP currently uses OAuth 2.1 with Dynamic Client Registration: the agent gets a new client_id at every server, and tokens are bearer tokens. The AAuth author points to MCP as a place where those limits already hurt. AAuth implementations for MCP already exist: a TypeScript SDK for MCP servers and an Envoy / agentgateway module that turns an MCP service into an AAuth resource.</p>
>>> <summary>Кто будет моим Person Server?</summary><p>Его выбираешь ты сам, его никто не навязывает. Это может быть сервис твоего провайдера входа, твоя компания (один сервер выполняет роли провайдера агентов, Person Server и Access Server для сотрудников) или даже свой собственный сервер. В спецификации есть раздел о том, как сделать минимальный Person Server.</p>
<<< <summary>Who will be my Person Server?</summary><p>You choose it; nobody imposes it. It could be a service from your sign-in provider, your company (one server acting as agent provider, Person Server and Access Server for employees), or even a server of your own. The spec has a section on building a minimal Person Server.</p>
>>> <summary>Зачем целых пять режимов? Не слишком сложно?</summary><p>Каждый сервис берёт только то, что ему нужно, и не обязан внедрять всё сразу. Обычно большинство адресов работают по личности агента или человека, и только несколько важных действий (оплата, запись, удаление) требуют полноценного разрешения.</p>
<<< <summary>Why five modes? Isn’t that too complicated?</summary><p>Each service takes only what it needs and doesn’t have to adopt everything at once. Usually most endpoints run on the agent’s or the person’s identity, and only a few important actions (payments, writes, deletes) need full authorization.</p>
